# Audio Assistant: минимальный мультиплатформенный MVP сборки

## Оценка исходного плана

Исходный план подходит для первого функционального инкремента, но слишком велик для цели «сначала довести проект до сборки». Процесс разработки и обязательные quality gates определены в `AGENTS.md`. В инкременте одновременно проверяются:

- C++/Qt/QML toolchain;
- архитектура контроллера и сервисов;
- асинхронные API;
- кольцевой аудиобуфер;
- инфраструктура Qt Test и минимальный smoke-тест;
- полноценная компоновка интерфейса.

Это увеличивает число возможных причин ошибки и затрудняет диагностику окружения. Для первого шага нужен минимальный вертикальный срез: CMake находит Qt, C++-код компилируется, QML включается в приложение, окно запускается и корректно закрывается.

Кольцевой буфер, интерфейсы транскрибации и LLM, аудиозахват, горячие клавиши и функциональные тесты следует реализовывать отдельными этапами после подтверждения базовой сборки.

## Цель этапа

Создать минимальный мультиплатформенный каркас desktop-приложения **Audio Assistant** на C++20, Qt 6, QML и CMake.

Целевые платформы:

- Linux;
- Windows;
- macOS.

Android является будущей целевой платформой и не входит в сборку или приёмку текущего desktop MVP.
Архитектура не должна без необходимости блокировать Android-порт, но Android-совместимость нельзя
заявлять до появления отдельной конфигурации сборки, платформенной реализации и реальных тестов.

Архитектура и сборочная система с первого этапа не должны привязывать проект к одной ОС. Общая
логика должна оставаться независимой от платформы, а неизбежные нативные интеграции должны быть
изолированы за узкими интерфейсами и подключаться через CMake. Фактическая сборка считается
подтверждённой только на тех платформах, где команды были реально выполнены; успешная проверка на
одной ОС не означает автоматическую проверку остальных или Android.

Результатом этапа должен быть проект, который:

1. Конфигурируется CMake в отдельном каталоге `build/`.
2. Собирается без ручного изменения сгенерированных файлов.
3. Запускает графическое Qt Quick-приложение.
4. Показывает минимальное окно с названием проекта и честным статусом текущей реализации.
5. Корректно закрывается.
6. Не содержит платформенно-зависимого кода, не изолированного средствами CMake или Qt.

На этом этапе важна только работоспособность toolchain и связки C++/QML. Функции будущего приложения не реализуются.

## Технологии

- C++20;
- Qt 6;
- Qt Quick;
- Qt Quick Controls;
- QML;
- CMake;
- Git.

Сторонние зависимости не добавлять.

## 1. Проверка окружения

До создания или изменения проекта проверить:

1. Доступный C++-компилятор и его версию.
2. Версию CMake.
3. Наличие Qt 6.
4. Наличие компонентов Qt Quick и Qt Quick Controls.
5. Наличие Ninja.
6. Наличие Git.

Предпочитать Ninja, если он доступен. Иначе использовать подходящий генератор CMake для текущей системы, например Visual Studio на Windows или Xcode на macOS. Проект не должен зависеть от конкретного генератора.

Не устанавливать пакеты автоматически. Если обязательных зависимостей нет, остановиться и сообщить:

- какой компонент отсутствует;
- какой командой или пакетом пользователь может его установить;
- какие проверки уже успешно пройдены.

Не создавать обходные заглушки вместо отсутствующего Qt.

## 2. Минимальная структура проекта

Создать каталог `audio-assistant/` со следующей структурой:

```text
audio-assistant/
├── CMakeLists.txt
├── README.md
├── .gitignore
├── src/
│   └── main.cpp
└── qml/
    └── Main.qml
```

Дополнительные исходные файлы создавать только при технической необходимости. Не создавать пустые каталоги и интерфейсы «на будущее».

## 3. Требования к CMake

Настроить проект следующим образом:

- указать минимальную версию CMake, совместимую с используемыми командами Qt 6;
- требовать Clang в строгом профиле и применять zero-warning policy из `AGENTS.md`;
- экспортировать `compile_commands.json` для статического анализа;
- включить C++20 через свойства конкретной цели;
- найти только реально используемые компоненты Qt 6;
- создать исполняемую цель `audio-assistant`;
- подключить QML через `qt_add_qml_module()`;
- использовать target-based команды CMake;
- обеспечить out-of-source сборку в `build/`;
- не использовать жёстко заданные системные пути, расширения исполняемых файлов и разделители каталогов;
- не добавлять обязательные для сборки флаги конкретного компилятора без проверки компилятора в CMake.

Не использовать глобальные `include_directories()` и `link_libraries()`.

На этом этапе не добавлять:

- Qt Multimedia;
- Qt Network;
- установку и упаковку приложения;
- платформенные hotkey-библиотеки;
- сторонние зависимости.

## 4. Минимальный C++ entry point

В `src/main.cpp`:

1. Создать `QGuiApplication`.
2. Создать `QQmlApplicationEngine`.
3. Загрузить корневой QML-компонент из QML-модуля.
4. Завершить приложение с ошибкой, если корневой QML-объект не был создан.
5. Запустить event loop.

Не добавлять `AppController` и бизнес-логику на этом этапе: для проверки сборки они не нужны.

Тонкий `main.cpp` допускается исключить из unit-тестирования как framework entry point. Это
исключение не распространяется на любой добавленный впоследствии модуль.

## 5. Минимальный QML-интерфейс

Создать одно окно Qt Quick Controls со следующими свойствами:

- заголовок `Audio Assistant`;
- разумный минимальный размер;
- тёмный фон;
- надпись `Audio Assistant`;
- статус `Каркас приложения собран. Функции пока не реализованы.`;
- кнопка `Close`, закрывающая приложение.

Интерфейс должен корректно отображаться при изменении размеров окна. Сложный дизайн, анимации, поля сервисов и неработающие кнопки `Start`, `Stop` и `Process` на этом этапе не нужны.

Не показывать фиктивные данные, успешный аудиозахват, транскрипцию или ответ LLM.

## 6. Документация

Создать краткий `README.md`, содержащий:

- назначение проекта;
- текущий статус: только собираемый GUI-каркас;
- требования к компилятору, CMake и Qt 6;
- команды конфигурации и сборки;
- команду запуска;
- список функций, которые пока не реализованы;
- краткий план следующих этапов.

README должен соответствовать реально проверенному окружению. Не указывать непроверенные команды как гарантированно рабочие.

## 7. Git

Создать `.gitignore` минимум для:

- `build/`;
- каталогов сборки IDE;
- локальных файлов IDE;
- временных файлов ОС.

Не выполнять `git commit`, если это отдельно не запрошено.

## 8. Qt Test и проверка результата

С первого этапа подключить `Qt6::Test`, `enable_testing()` и CTest. Добавить минимальный smoke-тест,
проверяющий загрузку корневого QML-компонента без ошибок. Тест должен работать с
`QT_QPA_PLATFORM=offscreen`, не требовать физического дисплея и не дублировать бизнес-логику.
Все последующие модули покрываются отдельными Qt Test-тестами согласно `AGENTS.md`.

После создания проекта выполнить реальную проверку из корня `audio-assistant/`.

Переносимый вариант с Ninja:

```bash
cmake -S . -B build -G Ninja
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Вариант с генератором CMake по умолчанию:

```bash
cmake -S . -B build
cmake --build build --parallel
```

После успешной сборки запустить приложение по фактическому пути, созданному выбранным генератором.

Пример для одноконфигурационного генератора на Linux:

```bash
./build/audio-assistant
```

Возможные варианты для других платформ и генераторов:

```text
Windows, Ninja:          build/audio-assistant.exe
Windows, Visual Studio: build/Debug/audio-assistant.exe
macOS application:      build/audio-assistant.app/Contents/MacOS/audio-assistant
```

Для многоконфигурационных генераторов конфигурацию необходимо задавать явно и одинаково для сборки и запуска:

```bash
cmake --build build --config Debug --parallel
```

Пути выше являются примерами. Использовать фактический путь, полученный в текущей конфигурации.

При наличии графической сессии проверить:

1. Окно открывается.
2. Заголовок и статус отображаются.
3. Кнопка `Close` работает.
4. В консоли нет ошибок загрузки QML-модулей.

Если графической сессии нет, не заявлять о визуальной проверке. В отчёте отдельно указать, что сборка завершена, но GUI не запускался либо запускался только с offscreen-платформой.

## 9. Ограничения этапа

В этот этап намеренно не входят:

- `AppController`;
- захват микрофона и системного аудио;
- кольцевой аудиобуфер;
- транскрибация;
- интеграция с LLM;
- сетевые запросы;
- горячие клавиши;
- выбор сервисов;
- многопоточность;
- функциональные модули сверх минимального QML smoke-теста;
- имитация будущих функций.

Отсутствие этих компонентов не является недоработкой текущего этапа.

## 10. Критерии завершения

Этап завершён только если:

- CMake успешно сконфигурировал проект;
- цель `audio-assistant` успешно собрана;
- строгая Clang-сборка не содержит предупреждений;
- форматирование, clang-tidy и доступные анализаторы прошли без замечаний;
- все Qt Test-тесты зарегистрированы в CTest и успешно прошли;
- ASan+UBSan прогон не обнаружил ошибок;
- QML встроен или корректно развёрнут средствами Qt/CMake;
- исходный код и CMake не содержат необоснованной привязки к Linux, Windows или macOS;
- приложение удалось запустить в доступном окружении;
- при доступном дисплее окно отображается и корректно закрывается;
- README содержит фактические команды сборки и ограничения;
- в отчёте нет утверждений о проверках, которые не выполнялись.

Если сборка невозможна из-за отсутствующей зависимости, результатом работы должен быть точный отчёт о блокере, а не частично проверенный проект, объявленный готовым. В отчёте явно перечислить платформы, на которых проект действительно проверен, и платформы, для которых совместимость только заложена архитектурно.

## 11. Формат итогового отчёта

В конце предоставить короткий отчёт:

1. Какие файлы созданы или изменены.
2. Какие версии компилятора, CMake, Qt, Ninja и Git обнаружены.
3. Каким генератором выполнена конфигурация.
4. Точная команда и результат сборки.
5. Выполнялся ли запуск приложения и каков результат.
6. На каких ОС выполнена реальная проверка.
7. Для каких ОС совместимость пока не подтверждена.
8. Создаёт ли изменение известные ограничения для будущего Android-порта.
9. Какие функции намеренно отложены.
10. Есть ли блокеры для следующего этапа.

## Следующие этапы

После успешного завершения build MVP развивать проект небольшими независимыми шагами:

1. Добавить `AppController`, свойства Qt и связь C++ с QML.
2. Добавить минимальные интерфейсы транскрибации и LLM без сетевых реализаций.
3. Реализовать `AudioBuffer` и покрыть его модульными тестами.
4. Подключить Qt Multimedia и захват одного аудиоисточника.
5. Добавить обработку последних 30 секунд.
6. Подключить реальные сервисы и обработку ошибок.
7. Добавить системный аудиовыход и глобальную горячую клавишу с учётом целевых платформ.
8. Настроить CI-матрицу минимум для Linux, Windows и macOS.
